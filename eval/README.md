# 평가셋

추천 결과를 사람 손 없이, 같은 잣대로 채점한다.

## 왜 있는가

모델을 바꾸거나 랭킹을 학습시킨 뒤 "나아졌는가" 를 말하려면 같은 자로 잰
숫자가 있어야 한다. 지금은 그 자가 없어서 "좋아 보인다" 밖에 말할 수 없다.

쓰이는 곳이 둘이다.

- 모델을 바꿀 때의 통과 기준 (지금 것보다 나빠지면 되돌린다)
- 랭킹을 손본 뒤의 효과 확인

하나를 만들어 두 곳에 쓴다.

## LLM 으로 채점하지 않는다

이 자를 쓰는 목적 하나가 "외부 모델 의존을 줄였는데 품질이 유지되는가" 다.
채점하는 쪽이 외부 모델이면 그 질문에 답할 수 없다 — 재는 자와 재는 대상이
같은 것에 묶인다.

그래서 여기에는 망을 타는 코드가 없고, 같은 입력이면 늘 같은 점수가 나온다.

## 다섯 축

| 축 | 무엇을 보는가 |
|---|---|
| schema | 결과가 약속된 형태인가 |
| grounded | 실측 후보로 골랐는가, 지어냈는가 |
| rules | 이동수단 반경을 넘긴 장소가 있는가 |
| route | 방문 순서가 장소 집합과 맞아떨어지는가 |
| timeline | 방문 시각이 하루 안에서 앞뒤가 맞는가 |

**읽을 때 주의.** 뒤의 세 축은 모델보다 검색·결정론적 노드의 영향을 크게
받는다. 세 축이 함께 움직였다면 모델이 아니라 그 앞단이 바뀐 것이다.
모델을 견줄 때 가장 먼저 보아야 할 축은 grounded 다.

## 쓰는 법

케이스 하나당 결과 파일 하나를 `<case_id>.json` 으로 모아 둔다. 내용은 완료
페이로드 그대로다. 학습 신호를 함께 모으면 grounded 축이 채워진다.

```
python -m eval.run --results out/gemini --training out/gemini-training
python -m eval.run --results out/gemini --baseline eval/baseline.json
python -m eval.run --results out/gemini --baseline eval/baseline.json --write-baseline
```

기준선을 주면 축마다 견주어, 나빠진 폭이 허용치를 넘을 때 0 이 아닌 값으로
끝난다. 사람이 표를 눈으로 대조하지 않아도 회귀가 드러난다.

**기준선 파일은 아직 없다.** 실제 실행 결과로 적어야 하기 때문이다. 만들어 둔
숫자를 넣으면 "재 봤다" 처럼 보이지만 아무 것도 재지 않은 것이 되고, 그 위에서
내리는 모델 교체 판단이 통째로 근거를 잃는다. 첫 실행 때 `--write-baseline`
으로 적는다.

종료값 규약:

| 상황 | 값 |
|---|---|
| 회귀 없음 | 0 |
| 기준선 대비 회귀 | 1 |
| 기준선 파일 없음 | 1 |
| 결과가 없는 케이스가 있음 | 1 |
| 기준선을 주지 않음(채점만) | 0 |

결과가 빠진 케이스에서 멈추는 이유: 조용히 넘기면 통과율이 남은 것들로만
계산돼 오히려 좋아 보인다.

## 케이스에 기대값을 적어 두는 이유

반경 같은 값은 hub 가 소유한다. 여기 코드에 상수로 두면 소유가 둘이 되어
어느 한쪽이 바뀔 때 조용히 어긋난다. 대신 케이스마다 **그 케이스가 기대하는
값** 으로 적는다 — 규칙이 바뀌면 케이스를 고쳐야 하고, 그 고침이 눈에 보인다.

## 아직 없는 것

- 외부 응답 고정(녹화). 지금은 결과를 밖에서 모아 와야 하며, 그 결과가 어떤
  외부 응답 위에서 만들어졌는지는 이 도구가 알지 못한다. 카카오·기상청 응답이
  달라지면 점수도 함께 흔들린다.
- 한국어 이유의 품질. 사람이 보는 수밖에 없다고 보고 축에서 뺐다.
